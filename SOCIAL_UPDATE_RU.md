# Anivibe — аватары, друзья и папки аккаунта (этап 2)

## Важно для установки

Это обновлённые исходники, НЕ собранная IPA. Новая миграция включена в архив, но на ваш Supabase здесь не применялась. Доступа к вашему backend не использовали.

Если предыдущие миграции уже применены, примените только:

`supabase/migrations/20261013040000_social_sharing_collections.sql`

Для новой установки применяйте все миграции в хронологическом порядке согласно основному README. Сначала сделайте резервную копию backend. Используйте обычный workflow миграций Supabase или SQL Editor; повторно запускать уже применённые миграции не нужно. Функцию `avatar` менять/заново развёртывать для этого обновления не требуется.

После миграции соберите `Anivibe.xcodeproj` в Xcode или запустите существующий GitHub Actions workflow. Подпись/секреты настраиваются как в исходном README.

## Аватары: что изменилось

Раньше каждый экземпляр ProfileAvatarView начинал с нового POST к Edge Function для подписания URL, затем AsyncImage делал отдельную загрузку изображения. Повторное открытие экрана не переиспользовало подготовленный аватар.

Теперь:

- Подписанные ссылки кэшируются до 40 секунд (сервер выдаёт их на 60 секунд), пустой результат — до 10 секунд.
- Одновременное получение одной ссылки объединено в одну задачу.
- Декодированные аватары кэшируются только в памяти: до 16 МБ / 64 записей, срок до 40 секунд; сетевой дисковый кэш отключён.
- Ключи включают ID смотрящего аккаунта, ID профиля и ревизию. Изменённое фото не получает старый кэш.
- При отсутствии avatar_path запрос вообще не выполняется.
- После загрузки своего профиля и списка друзей выполняется ограниченный предварительный прогрев аватаров.
- Смена аккаунта/фото/отношений очищает декодированные аватары. Поздние ответы проверяются перед отображением.

Первый показ фотографии всё ещё требует сети и работы Supabase Edge Function. Численные измерения ускорения не проводились; полностью исключить первую сетевую задержку кэшем нельзя. Подписанные ссылки остаются краткоживущими и приватный bucket не становится публичным.

## Друзья и профиль друга

Вкладка друзей:

- «Друзья», «Заявки» и «Поиск» разделены сегментами.
- Карточки с аватарами, именами, username и переходом в профиль.
- Отдельные входящие/исходящие заявки; принять/отклонить/отменить/удалить.
- Поиск после паузы 350 мс, от 3 символов; поддерживается ввод с @.
- Состояния загрузки/пустого списка/ошибки и обновление жестом.

Профиль друга:

- Крупный аватар, имя, username, описание и действие дружбы.
- Реальный счётчик друзей и просмотренных тайтлов, если разделы разрешены.
- Список доступных вам профилей его друзей.
- Недавняя история с сериями и датами, полная история с подгрузкой страниц по 40 строк.
- Статистика библиотеки и полный список тайтлов с подгрузкой страниц по 40 строк.
- Переход к карточке аниме. Любые действия со списками на странице аниме относятся к ВАШЕЙ библиотеке; библиотека друга доступна только для чтения.

Приватность:

В редакторе профиля добавлены независимые настройки для друзей, истории и библиотеки: **Только я / Друзья / Все пользователи**. По умолчанию все три раздела закрыты — существующая история не публикуется автоматически. Чтобы друг увидел историю, владелец должен включить для неё «Друзья» или «Все пользователи» и синхронизировать свои просмотры.

Публичная настройка раздела не обходит приватность самого профиля. В чужом списке друзей не раскрываются закрытые профили, к которым у смотрящего нет доступа. Поэтому общий разрешённый счётчик друзей может отличаться от числа видимых профилей.

Почта, точная позиция/длительность плеера и папки остаются личными. Таблицы истории/библиотеки по-прежнему доступны напрямую только владельцу. Чтение разрешённых социальных разделов идёт через отдельный RPC с проверкой auth.uid(), а не через широкую SELECT-политику.

Пагинация истории/библиотеки использует offset и стабильную сортировку с ID. При изменениях у владельца во время чтения список стоит обновить жестом; это не неизменяемый серверный снимок.

## Папки аккаунта

- Отдельный локальный файл `collections-user-<uuid>.json` для каждого аккаунта.
- Гостевые папки остаются в `collections.json`; они не загружаются в произвольный аккаунт автоматически.
- Новые папки аккаунта, названия, содержимое, порядок папок и тайтлов, удаления синхронизируются в том же цикле, что и библиотека.
- Автосинхронизация через 8 секунд после последнего изменения, при запуске/возврате приложения, а также по кнопке в профиле.
- В облако отправляются только ещё не подтверждённые изменения папок; получение — постраничное, собственные записи аккаунта.
- Удаления сохраняются как tombstones: старое устройство не должно возвращать ранее удалённую папку.
- Изменения, внесённые во время сетевого запроса, объединяются с ответом, а не заменяются исходным старым снимком. Если синхронизация уже идёт, следующий запрос не теряется.
- Ошибка открытия локального файла не перезаписывает его; при ошибке смены хранилища личные данные скрываются до восстановления.

### Как перенести существующие папки

Войдите в нужный аккаунт → Профиль → раздел «Синхронизация» → **Скопировать локальные папки в аккаунт** → подтвердите → **Синхронизировать сейчас**.

Старые папки не удаляются. Импорт создаёт новые ID и добавляет папки к имеющимся папкам аккаунта; повторный импорт создаст копии. После успешной синхронизации папки можно получить при входе в тот же аккаунт на другом устройстве.

### Конфликты и ограничения

Разные папки объединяются независимо. Единица конфликта — папка целиком, включая порядок тайтлов: при одновременном редактировании одной папки на двух устройствах побеждает более поздняя версия по updated_at, при равенстве — mutation_id. Это НЕ поэлементное слияние изменений внутри одной папки. Удаление тоже участвует в этом правиле. Порядок папок хранится в rank с детерминированным дополнительным порядком по UUID.

Сервер ограничивает название 120 символами, содержимое — 2000 тайтлов, JSON папки — 2 МБ. Настройки темы/фона по-прежнему локальные. Синхронизация библиотеки и папок последовательная, не общая транзакция: библиотека может успеть обновиться, даже если этап папок завершился ошибкой; повторная синхронизация продолжит работу.

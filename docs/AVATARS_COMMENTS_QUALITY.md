# Аватары, комментарии и качество видео

Это полный проект на прежней основе. Настройки Supabase клиента сохранены. Выбор озвучки не удалён.

## 1. Обновить проект целиком (Windows)

1. Распаковать ZIP **в отдельную папку**, не внутрь папки исходников `Anivibe/Anivibe`.
2. Сделать резервную копию своих изменений. Запустить `UPDATE_WINDOWS.cmd` из корня распакованного проекта: он заменяет управляемые папки проекта в `%USERPROFILE%\Downloads\Anivibe`, сначала перемещая прежние папки в резервную копию рядом с репозиторием. `.git` сохраняется, `Config\Secrets.xcconfig` восстанавливается. Это предотвращает конфликты от лишних старых Swift-файлов. Локальные изменения исходников останутся в резервной копии, а не в новой версии. Другую папку репозитория можно передать первым аргументом.
3. Проверить `git diff --stat`. Файлы новой миграции, `supabase/functions/avatar` и `Packages/AnivibeCore` тоже должны попасть в коммит.
4. Не коммитить свои секреты; `.gitignore` исключает обычные конфиги секретов, но не любые произвольно названные файлы.

```bat
cd /d C:\Users\ninaa\Downloads\Anivibe
python scripts\check_project.py
git status --short
git add -A
git commit -m "Add avatars comments and restore quality controls"
git push origin main
```

Actions → iOS → артефакт IPA. IPA неподписанный; для установки нужна подходящая подпись. Workflow запускает проверки, затем компилирует iOS на macOS. Локальная проверка синтаксиса Swift не заменяет сборку Xcode.

## 2. Новая SQL-миграция — выполнить один раз

Supabase Dashboard → SQL Editor → New query. Вставить **весь** файл:

`supabase/migrations/20261013030000_avatars_comments.sql`

Нажать Run. Он предполагает, что четыре предыдущие миграции уже применены (включая profiles_friends). Старые таблицы библиотеки и истории не удаляются. Не выполнять `db reset` и не повторять старые миграции. Если новая миграция уже успешно выполнена, повторно её запускать не нужно. Транзакция откатывается при ошибке; сохраните текст ошибки.

Миграция создаёт приватный bucket `avatars`, серверные лимиты, таблицы комментариев/реакций/жалоб, RPC и ограничения доступа. Комментарии работают после SQL-миграции; функция ниже нужна только для аватаров.

## 3. Развернуть функцию avatar

Нужен Node.js/npm. В терминале **из корня репозитория** (того, где `supabase` и `Anivibe.xcodeproj`):

```bat
npx supabase@latest login
npx supabase@latest link --project-ref kdbkkigoefierimdzdrq
npx supabase@latest functions deploy avatar --project-ref kdbkkigoefierimdzdrq --no-verify-jwt --use-api
```

CLI может попросить авторизацию или пароль БД при link — вводить локально, не в чат/исходники. Docker/локальный Supabase для этих функций приложения не нужен; если CLI требует Docker для упаковки, используйте поддерживаемую CLI опцию `--use-api` при deploy или установите Docker согласно документации CLI.

`--no-verify-jwt` отключает только шлюзовую проверку: **сама функция обязательно вызывает Supabase Auth `getUser()` и отклоняет неверный пользовательский JWT**. Это нужно для совместимости с современными ключами подписи проекта. Клиентский publishable key не даёт доступ без входа. Не удалять эту проверку из `index.ts`.

`SUPABASE_URL`, `SUPABASE_ANON_KEY` и `SUPABASE_SERVICE_ROLE_KEY` предоставляются средой Supabase Edge Functions. Service-role работает только на сервере, в приложение не добавляется. Не присылайте его в чат и не вставляйте в Config.

После deploy проверить функцию `avatar` в Dashboard → Edge Functions. Ошибки загрузки смотреть в её логах (токены и исходные фото функция не печатает).

## 4. Как проверить на телефоне

### Аватар

Профиль → Редактировать → Выбрать из галереи. Фото сохраняется сразу, независимо от кнопки сохранения имени. Предварительная обработка ограничивает размер до 512 px; исходный файл до 25 МБ. Сервер принимает до 1 МБ JPEG, проверяет заголовок/размеры, декодирует и заново кодирует изображение без EXIF/комментариев. Не принимает произвольный файл по одному MIME-заголовку. До 10 изменений в час (невалидные попытки тоже учитываются).

Аватар виден в своём профиле, открытом доступном профиле и комментариях. Закрытый профиль и его аватар видны только разрешённым пользователям. Другим показывается стандартная иконка. Чтение через короткую подписанную ссылку (60 секунд), не через публичный bucket. Уже загруженную картинку или выданную на 60 секунд ссылку невозможно мгновенно отозвать при смене приватности. Кеширование фото системой также не равнозначно немедленному отзыву.

Удаление аватара очищает профиль и удаляет заменённый объект. При аварии функции/сбое удаления возможны неиспользуемые объекты: администратор может удалить файлы, на которые не ссылается `profiles.avatar_path`, оставив запас времени для текущих загрузок. Автоматический сборщик таких объектов пока не добавлен.

### Комментарии

Открыть тайтл → блок «Комментарии» ниже серий/озвучек. Требуется вход. Отправить сообщение, затем проверить на втором аккаунте. Есть «Новые»/«Популярные», страницы по 20, лайк/дизлайк/снять реакцию, удаление своего сообщения и жалоба на чужое. Текст показывается как обычный текст, не выполняется как HTML.

Ограничения: 1–2000 символов; не чаще сообщения в 15 секунд, до 30 сообщений в час; повторный текст в течение 20 минут отклоняется; общий лимит действий 200 в час с паузой минимум 1 секунда. До 10 уникальных жалоб в сутки. Правила проверяются на сервере под блокировкой пользователя. Гости не читают комментарии в этой версии. Это не live-чат: новые сообщения появятся по кнопке «Обновить».

Автор приватного профиля отображается как «Пользователь» для людей без доступа к профилю. Свой профиль/друзья/публичный профиль видны согласно прежним RLS-правилам. Публикуемый текст комментария виден всем вошедшим пользователям, даже при приватном профиле.

Жалобы реально сохраняются, но **нет автоматического решения нейросетью или отдельного интерфейса модератора**. Администратор проверяет очередь в Supabase SQL Editor:

```sql
select r.comment_id, r.reason, r.created_at, c.body
from public.comment_reports r join public.title_comments c on c.id=r.comment_id
order by r.created_at desc;
-- Только после проверки конкретной жалобы:
-- update public.title_comments set state='hidden' where id='UUID комментария';
```

### Качество

В нативном плеере — отдельная видимая кнопка «Качество: …». Открывает настройки видео, разрешения идут первым разделом; текущий вариант отмечен. В отдельном плеере Kodik — меню «Качество: …» под заголовком. Варианты берутся из ответа источника, а не из фиктивного списка. Обычно это 360p/480p/720p/1080p; если источник отдаёт другой набор, отображается именно он. 460p не добавляется вместо 480p без потока такого разрешения.

После переключения проверить восстановление позиции, паузу и скорость. Выбранный предел качества Kodik запоминается. При адаптивном HLS без отдельных ссылок показано объяснение автоматического качества. В веб-плеере качество меняется средствами самого сайта.

## Проверки и границы

В проекте добавлены тесты сетевых запросов и смены аккаунта, SQL-тесты прав/реакций/жалоб/лимитов, Deno-тесты проверки JPEG. GitHub Actions также проверяет TypeScript и миграции перед сборкой IPA. Нет утверждения, что приложение уже запускалось на iPhone или что новые SQL/Edge функции уже развёрнуты в вашем проекте: их нужно применить шагами выше.
